# Write your first custom rule

The full rule format (`rules:` in `rules.yaml`, or YAML frontmatter in `AGENTS.md`/
`CLAUDE.md`) is the same rich shape keel's own 47 shipped rules use — `id`, `type`,
`level`, `scope`, `context`, `action`, `message`, `priority`, plus a couple dozen more
fields depending on `type`. That's the right shape for keel's own catalog. It is not a
reasonable first thing to hand someone who just wants to block one command their team
keeps running by accident.

`simple_rules:` is the minimal-fields form for that case. Five fields, total:

- `id` — a unique name for the rule
- `type` — one of `command`, `filesystem`, `content`, `env`, `network`
- one match-condition field, chosen by `type` (see the table below)
- `action` — what to do when it matches (`block`, `deny`, `warn`, `prompt`, `allow`, `fix`, `report`, `research`, `redirect`)
- `message` — what to tell the person or agent that triggered it

Everything else — `level`, `scope`, `context`, `priority`, `mode` — is filled in for
you: `level: sprint` (no floor — the rule is evaluated at every dial, and obeys the
same warn-once-then-block / sprint-softens-deny-to-warn behavior every other unleveled
rule gets; see `docs/tiers.md`) and `context: [both]` (fires locally and in CI). You
never write those unless you outgrow the minimal form.

`priority` is filled in too, at **-100** — deliberately, and lower than any of keel's
own shipped default rules (the lowest of which sits at -10). Rules with no declared
priority sort at 0 by default, so without this a broad `simple_rules:` entry could
silently out-rank and shadow a more specific shipped default that matches the same
command — e.g. a `simple_rules:` rule allowing `cat`/`less`/`head`/`tail` broadly would
otherwise evaluate *before*, and shadow, the shipped `secret-file-read-without-egress`
warn on `cat .env` (keel evaluates rules in priority order, first match wins).
`simple_rules:` entries defer to the shipped catalog by design; there is currently no
way to opt a minimal-form rule into a higher priority — if you need that, write the
rule in the full `rules:` form instead.

| `type`         | match-condition field | what it matches                          |
|----------------|------------------------|-------------------------------------------|
| `command`      | `match` or `match_regex` | the command text keel is about to run   |
| `filesystem`   | `paths`                 | file paths being written/deleted/globbed |
| `content`      | `patterns`              | file content being written                |
| `env`          | `vars`                  | environment variable names                |
| `network`      | `match`                 | the domain/URL being requested            |

A `simple_rules:` entry lives right alongside `rules:` in the same file — you can mix
full-form and minimal-form rules freely, and a minimal-form rule is enforced exactly
the same way a full-form one is (it's expanded into one before keel ever evaluates
it). If you need anything past a plain match condition — an `unless` exemption, a
`priority`, a non-default `level`, or one of the other dozen-odd rule types (`rate`,
`sequence`, `verification`, ...) — write that rule in the full `rules:` form instead;
`simple_rules:` intentionally doesn't try to cover everything.

## Example 1 — block a project-only footgun command

Say your team has a script that resets the shared staging database, and it's been run
against production by accident twice. Block the literal command:

```yaml
version: 1
simple_rules:
  - id: no-prod-db-reset
    type: command
    match: "reset-db(\\.sh)?\\s+--env(=|\\s+)prod"
    action: deny
    message: "reset-db --env prod is blocked here — use --env staging, or run it by hand with extra care if you really mean production."
```

Save this as `.keel/rules.yaml` in your project (or add the `simple_rules:` block to
your existing one) and run `keel validate` to confirm it loads.

## Example 2 — warn on a risky file pattern

Your project vendors a generated client that nobody should hand-edit (it gets
overwritten on the next `codegen` run, silently losing the edit). A `warn` catches it
without blocking legitimate work:

```yaml
version: 1
simple_rules:
  - id: no-hand-edit-generated-client
    type: filesystem
    paths: ["src/generated/**"]
    action: warn
    message: "src/generated/** is regenerated by `npm run codegen` — edits here are lost on the next run. Edit the source schema instead."
```

## Example 3 — catch a pattern in file content

Blocking a specific command doesn't help if the risk is *what gets written*, not
*what gets run*. Catch a hardcoded API key pattern before it lands in a file:

```yaml
version: 1
simple_rules:
  - id: no-hardcoded-api-key
    type: content
    patterns:
      - "sk-[a-zA-Z0-9]{20,}"
    action: block
    message: "That looks like a hardcoded API key. Use an environment variable or your secrets manager instead."
```

`patterns` here is a plain list of regex strings — no `{regex: ...}` wrapper needed;
that's the one place `simple_rules:` genuinely simplifies on the full form's shape,
not just on which fields you have to fill in.

## What you get for free, and what you don't

A `simple_rules:` entry becomes a completely ordinary rule once loaded — it
participates in the same project/global/local hierarchy, the same `keel level` speed
dial, the same warn-once-then-block escalation on `action: deny`, and shows up the
same way in `keel status` and `~/.keel/traces/*.jsonl`. There is no separate "simple
mode" enforcement path to keep in sync with the real one.

What you don't get from the minimal form: `unless`/`unless_reasoning` exemptions, a
custom `priority`, `level: protect` (an un-bypassable floor — deliberately excluded
from the minimal form so a beginner rule can't accidentally become one), and any rule
`type` outside the five above (`rate`, `time`, `sequence`, `verification`, `flow`,
`stuck`, `research`, `diagnosis`, `claim`, `oracle`, `package`, ...). Those all need
the full `rules:` form — see the `## Rules` section of the top-level README for a
complete worked example, and `docs/tiers.md` for how `level`/`mode` interact with the
speed dial.

## Getting the error messages right

If a `simple_rules:` entry is missing something required, `keel validate` (and the
loader itself) reports a specific, plain-language error instead of a generic schema
dump — for example:

```
rule 'no-prod-db-reset': type 'command' requires a 'match' or 'match_regex' field (the command text or pattern to catch)
```

rather than a bare "invalid rule" or a JSON Schema stack trace. Fix the named field
and re-run `keel validate`.
