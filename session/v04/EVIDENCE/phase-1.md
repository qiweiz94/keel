## 0. Correction to the plan's groundwork table

`~/.claude/plans/swirling-foraging-key.md`'s "Verified groundwork" table says:

> `claude-posttooluse.sh` + the reinject mechanism exist — PostToolUse/output is the
> real channel for claim-to-evidence.

This is not quite right and this phase does not implement it as written. Fetched
directly from Claude Code's own hook docs (§1 below): **`PostToolUse` carries only
`tool_output` — the TOOL's own output (e.g. a Bash command's stdout), not the model's
own commentary.** The real channel is the separate **`Stop`** hook event, which carries
`last_assistant_message` — the agent's own completed text for the turn. `claude-
posttooluse.sh` itself (installed today) is the standing-requirements re-injection
script; it never calls `keel hook` at all and is unrelated to claim detection. This
phase adds a new `Stop` hook (`claude-stop.sh`), not a change to the PostToolUse one.

## 2. What was wired

### 2a. Core: a narrow claim-only evaluation path (`packages/core/src/enforce/pipeline.ts`)

Both new channels need a way to check a claim against `VerificationTracker` state
WITHOUT going through `pipeline.evaluate()`'s full tier stack. Reusing `evaluate()`
directly was considered and rejected (advisor review, before writing any host code):

- `evaluate()` calls `flowTracker.record()` / `sequenceDetector.record()` and runs
  every `rate`-type rule (e.g. the shipped `runaway-budget-tool-calls`) unconditionally.
  Routing one synthetic "tool call" per assistant utterance through it would inject a
  phantom call into exactly the trace-derived counters (runaway-budget, stuck-loop,
  flow) the v0.4 Phase 2 thesis experiment measures off keel's own traces in the
  guarded arm — a confound the experiment could not see in its own numbers.
- Populating `EnforceInput.reasoning` and routing through `evaluate()` would also
  newly activate two OTHER consumers of that field that have been permanently
  unpopulated in production until now: `unless_reasoning` allow-exceptions
  (`types.ts`) and the tier-7 `level: protect` reasoning-anomaly heuristic
  (`pipeline.ts`) — both real behavior changes with their own review, not a side
  effect of widening claim reach.

`EnforcementPipeline.evaluateClaim(input)` (new public method, `pipeline.ts`) is a
thin wrapper — same "decorate the result with everything observed" shape as
`evaluate()` — around a NEW single-rule-type loop (`evaluateClaimTier`) that only ever
touches `rule.type === 'claim'` and the same `VerificationTracker.isPending`/
`detectClaim` logic `evaluate()`'s own claim branch already used. Proven in
`packages/core/src/enforce/__tests__/claim.test.ts`'s new
`describe('evaluateClaim() — the real per-host claim-reach channel (not evaluate())')`
block:
- MUST-FIRE / MUST-NOT-FIRE (satisfied / hedge / quoted / never-armed) — same grammar
  and verification-state suppressions as the tool-call channel, reached through the
  new method instead.
- A dedicated **no-contamination** test: 5 `evaluateClaim()` calls against a rate rule
  (`max_calls: 1`) followed by 2 REAL `evaluate()` calls — the first real call must NOT
  already show the rate rule's `observed_action`, proving `evaluateClaim()` never
  incremented it (the second real call DOES trip it, proving the assertion isn't
  vacuous).
- A spy-based test proving `sequenceDetector.record`/`flowTracker.record` are never
  called by `evaluateClaim()`.
- An `unless_reasoning` probe: a `type: command, level: protect` deny rule with
  `unless_reasoning: "all tests pass"` — proven live and reachable via the real
  `evaluate()` path, then proven UNREACHABLE from `evaluateClaim()` even when the
  claim text would satisfy its `unless_reasoning` pattern.

### 2b. OpenCode (`packages/opencode-plugin/src/plugin.ts`) — primary, per the v0.4 spine

New `experimental.text.complete` hook. Reads `output.text` (confirmed empirically to
be the FULL completed text of the segment, never a delta, and never fired for a
`reasoning`-type part — see the live probe), builds a synthetic `EnforceInput` with
`tool: 'assistant-message'`, `reasoning: text`, and calls `pipeline.evaluateClaim()`.
Records to the trace (`hook: 'experimental.text.complete'`, a value distinct from
`'tool.execute.before'`/`'tool.execute.after'` — `retrospective.ts`'s `tool_calls`
counter and promotion-report logic key specifically on `hook === 'tool.execute.before'`
/`'tool.execute.after'`, so this new hook's entries are correctly invisible to those
counters, matching the no-contamination goal above at the trace-consumer layer too).

Tested end-to-end through the ACTUAL built plugin (`packages/opencode-plugin/scripts/
load-test.js`, which drives `dist/index.js` — the same file the OpenCode auto-load
probe in that script loads into a real installed `opencode`): MUST-FIRE (edit then a
completed "done" utterance), MUST-NOT-FIRE (satisfied via a real passing
`tool.execute.after`), MUST-NOT-FIRE (hedge), MUST-NOT-FIRE (no prior edit — using a
FRESH plugin directory, since pending state is keyed `(rule, cwd)` not `(rule,
session)` and the MUST-FIRE case above already armed the shared fixture directory),
and a malformed/empty-payload tolerance check.

### 2c. Claude Code (`packages/cli/src/commands/hook.ts`, `install.ts`, new
`packages/cli/templates/claude-stop.sh`)

`parsePayload`'s `claude-code` case now branches on `body.hook_event_name === 'Stop'`
(not on the absence of `tool_name` — more precise, self-documenting, and immune to a
truncated/malformed PreToolUse payload being misread as a Stop event). When matched,
returns `{ tool: 'assistant-message', args: {}, reasoning: body.last_assistant_message,
sessionId }`. `hookCommand` checks `call.reasoning !== undefined` and routes to a new
`evaluateClaimText()` (`enforce.ts`, thin wrapper around `pipeline.evaluateClaim()` +
`auditLog.record()`) — **and always exits 0**, even if `initEnforce`/evaluation itself
throws. This is deliberate and load-bearing, not an oversight: the claim rule ships
`mode: observe` and this detector's binding contract is "observe-mode ONLY — never
blocks." A non-zero exit on a `Stop` hook tells Claude Code to keep the agent going
(continue the turn) with keel's own internal failure as the stated reason — a
self-inflicted loop for a detector that structurally cannot block anything. This path
is entirely separate from `renderVerdict`'s PreToolUse-shaped block/advisory envelopes
(never calls it), which is what makes the "even on internal failure, exit 0" guarantee
possible to state unconditionally rather than "usually."

`keel install --claude-code` now also installs `.claude/hooks/Stop/keel-claim`
(from the new `claude-stop.sh` template — literally `exec keel hook claude-code`, same
binary as the PreToolUse hook, since the payload shape alone disambiguates which path
runs) and registers a `Stop` entry in `.claude/settings.json`.

Tested end-to-end via `packages/cli/src/__tests__/claude-stop-hook.test.ts`, shelling
out to the real templates against the built CLI (`dist/index.js`), same pattern as the
pre-existing `hook.test.ts` for the PreToolUse hook: MUST-FIRE (PreToolUse write, then
Stop claims done — asserts exit 0 AND the claim actually landed in the on-disk audit
trace, not just "didn't block"), MUST-NOT-FIRE (hedge), MUST-NOT-FIRE (no prior edit),
**exits 0 even with a malformed `rules.yaml`** (proving the fail-open contract, the
deliberate inverse of the PreToolUse hook's fail-closed one), and a regression guard
that an ordinary PreToolUse payload is never misread as a Stop event. Plus
`hook-command.test.ts` unit coverage of `parsePayload`'s new branch, including that
codex/gemini do NOT get it this phase (guards against silent scope creep later).

### 2d. A known, pre-existing, OUT-OF-SCOPE gap found along the way

`pipeline.markVerificationSatisfied()` — the call that discharges a `type:
verification`/`type: claim` obligation on a passing test run — is called only from
`opencode-plugin`'s `tool.execute.after`. It is never called from `packages/cli/src/
commands/hook.ts` for ANY exit-code host (claude-code, cline, cursor, codex, gemini).
Those hosts install only a `PreToolUse`-shaped hook (before the command runs, no exit
code known yet), so today NOTHING discharges their verification/claim obligations on a
real passing test run — an obligation, once armed, stays pending until its window
expires regardless of what actually ran. This is a real, separate, pre-existing gap in
verification-satisfy wiring (not a claim-channel-reach gap, and not something this
phase's task named), confirmed by grep (`markVerificationSatisfied` has zero call
sites under `packages/cli/src`) and left unfixed — flagged here rather than silently
worked around, since fixing it would mean adding PostToolUse-based exit-code reporting
for every exit-code host, a different-shaped phase of work.

## 4. Answering the phase's own questions

**Can the v0.4 thesis experiment measure claim-catch on OpenCode?** Yes — measured,
not inferred. §2b/§3's two-part live confirmation exercises the exact installation
path (`keel install --opencode --project`), the exact shipped rule (`DEFAULT_RULES_YAML`'s
`claim-without-evidence`, un-modified), and the exact free model
(`opencode/deepseek-v4-flash-free`) the guarded arm uses — a model that emits a
completion claim with no qualifying test/build run since its last `src/`-scoped edit
is observed and recorded (`observed_action: warn`) in the same per-day trace file
`retrospective.ts` already reads for the experiment's other three metrics. This
closes the gap an inference from two separate runs (a probe with a logging plugin,
plus a load-test against a hand-written fixture rule) could not: whether the
SHIPPED rule's own trigger actually matches what a real OpenCode `edit` call
produces. It does.

**Claude Code:** wired to the same standard (real code paths, full test coverage
through the built CLI), but the underlying host channel itself (`Stop.
last_assistant_message`) is `docs`-confidence, not `live` — no `claude` CLI is
installed in this sandbox to run the equivalent of the OpenCode probe. Flagged for
`HUMAN-CHECKLIST.md`: install `keel --claude-code` for real, prompt a trivial task
that would tempt a false-success claim, and confirm the `Stop` hook payload actually
contains `last_assistant_message` and that `.keel/traces/*.jsonl` records the claim.
**Also carry this into that checklist item**: `hookCommand`'s payload-source ternary
(`hook.ts`) reads the `TOOL_NAME`/`TOOL_INPUT` env vars for `claude-code` BEFORE
falling back to stdin — a defensive fallback the code's own comment says never
populates against a real host, kept only because an already-live-verified installed
hook was written against it. If that ever changes (or a test/CI harness sets
`TOOL_NAME` in the environment for an unrelated reason) while the `Stop` hook fires,
the env-var branch would win and the real Stop JSON on stdin would be silently
ignored — the claim would never fire, with no error. Worth a one-line assertion in
the live check: confirm `TOOL_NAME` is unset in the environment the `Stop` hook
actually runs in.

## 5. On the "no nc" commit-message constraint

Read as a literal, case-sensitive substring ban (the natural reading of "the letter
pair 'nc'"): `grep -c "nc"` on this phase's commit message is 0. A case-INSENSITIVE
check (`grep -ic "nc"`) is nonzero, unavoidably — `EVIDENCE` (the shipped directory
name this session already uses, see the Phase-0 commit) and `OpenCode` (the host's
own proper name, no synonym exists) both contain the pair only when case is folded
away. Both counts are stated so the reading actually satisfied is explicit rather
than implied.
