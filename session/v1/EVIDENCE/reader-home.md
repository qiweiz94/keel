# LANE M1r-3b — reader-side KEEL_HOME consistency (closes the split-brain)

Branch: `v1-reader-home` (based on `v0.4-thesis` with wave-1 hardening merged,
including M1r-3's install-side `KEEL_HOME` and M3's path-normalize util)
Worktree: `/Users/nanoclaw/code/keel-v1-reader-home`

## Summary

M1r-3 made `install()` honor `KEEL_HOME` across all 10 global write targets,
but explicitly stopped short of the reader side and filed it as follow-up
(see `session/v1/EVIDENCE/m1r-3-install.md`). This lane closes that gap:
every reader that used to resolve a bare `homedir()` for a `.keel`-relative
path now goes through the same `resolveHome()` install.ts uses, so an
install under `KEEL_HOME` and every subsequent read agree on where keel's
state lives.

**Shared resolver**: `packages/core/src/home.ts`

```ts
export function resolveHome(): string {
  return process.env.KEEL_HOME || process.env.HOME || homedir()
}
```

Precedence: `KEEL_HOME` (new, the override that closes the split-brain) >
`HOME` (preserves `rule-parser.ts`'s pre-existing Windows-safety behavior —
`os.homedir()` ignores `$HOME` on Windows, reading `USERPROFILE` instead,
and several tests sandbox by setting `process.env.HOME`) > `os.homedir()`
(the final fallback, unchanged from before).

Exported from two entry points so every consumption boundary can reach it
without a hand-edit of generated code:
- `packages/core/src/index.ts` — the `@get-keel/core` npm-package barrel
  (consumed by `packages/mcp-server`, which imports `from '@get-keel/core'`).
- `packages/core/src/keel-core.ts` — the plugin-bundle entry point (bundled
  by esbuild into `packages/cli/templates/keel-enforce.js`; consumed by
  `packages/opencode-plugin/src/plugin.ts`, which imports straight from
  `../../core/src/keel-core.js`, its existing pattern for every other
  core export it uses).

CLI commands (which already deep-import generated copies like
`from '../core/enforce/overrides.js'`) import the copy at
`packages/cli/src/core/home.ts` — generated by the existing build step
(`fs.cpSync('../core/src', './src/core', ...)` in `packages/cli/package.json`)
from the same `packages/core/src/home.ts` source. No hand-edits of
`packages/cli/src/core/**` or `templates/keel-enforce.js` were made; both
were regenerated by `npm run build`, and `diff -rq packages/core/src
packages/cli/src/core` (excluding `__tests__`) is empty after the build.

## 2. Unifying the pre-existing `*_DIR` overrides under `KEEL_HOME`

Four narrower env vars already existed and are preserved with their exact
prior precedence — the specific var still wins outright when set; only the
*fallback* (previously a bare `homedir()`) now routes through
`resolveHome()`:

| Var | Reader(s) | Before | After |
|-----|-----------|--------|-------|
| `KEEL_STATE_DIR` | `state-manager.ts` (`stateDir()`), `problem-ledger.ts` (`ledgerPath()`), `package-verifier.ts` (`packageVerifierStateDir()`) | `process.env.KEEL_STATE_DIR \|\| join(homedir(), '.keel', 'state')` | `process.env.KEEL_STATE_DIR \|\| join(resolveHome(), '.keel', 'state')` |
| `KEEL_TRACES_DIR` | `audit.ts` (`AuditLog` constructor — explicit `logDir` arg still wins over both), `retrospective.ts`, `opencode-plugin/plugin.ts` | `process.env.KEEL_TRACES_DIR \|\| join(homedir(), '.keel', 'traces')` | `process.env.KEEL_TRACES_DIR \|\| join(resolveHome(), '.keel', 'traces')` |
| `KEEL_RESEARCH_CACHE_DIR` | `research-cache.ts` (`researchCacheDir()`) | `process.env.KEEL_RESEARCH_CACHE_DIR \|\| join(homedir(), '.keel', 'cache', 'research')` | `process.env.KEEL_RESEARCH_CACHE_DIR \|\| join(resolveHome(), '.keel', 'cache', 'research')` |
| `KEEL_OVERRIDES_DIR` | `overrides.ts` (`FileRuleOverrideStore` constructor default param `home`), `allow.ts` (`overridesDirectory()`) | `process.env.KEEL_OVERRIDES_DIR \|\| join(home, '.keel')` where `home` defaulted to bare `homedir()` | same shape, but the constructor's default param is now `home = resolveHome()`; `allow.ts`'s own fallback is `join(resolveHome(), '.keel')` |

All four call-time-not-module-load-time contracts were preserved exactly
(no new module-level consts introduced anywhere in `packages/core/src`) —
confirmed by the full test suite, since `state-manager.test.ts` and
`package-verifier.test.ts` both explicitly assert a second construction in
the same process picks up a changed env var.

## 3. Tests updated in lockstep (not new behavior, just kept in sync)

Three test files independently recomputed `pipeline.ts`'s `DISABLED`
sentinel path inline (`join(homedir(), '.keel', 'DISABLED')`) rather than
importing it, so once `pipeline.ts` started resolving via `resolveHome()`
these would have silently diverged from the code under test whenever
`KEEL_HOME`/`HOME` differs from `homedir()`'s output:

- `packages/core/src/enforce/__tests__/pipeline.test.ts`
- `packages/core/src/enforce/__tests__/shell-normalize-bypass.test.ts`
- `packages/core/src/enforce/__tests__/threat-model.test.ts`

All three now import `resolveHome` from `../../home.js` and use it for the
same "clean up a developer's live kill switch before running unit tests"
`beforeAll` check, mirroring `pipeline.ts` exactly.

## 4. Install → read consistency test (new)

Added to `packages/cli/src/__tests__/install.test.ts`, in a new
`describe('install → read consistency under KEEL_HOME (M1r-3b)')` block.
Both tests drive the REAL built CLI (`node dist/index.js ...`) as separate
processes per step — not in-process unit calls — with two DISTINCT tmp
dirs for `HOME` and `KEEL_HOME` throughout (so a reader/writer that fell
back to `homedir()`, which resolves the `HOME` dir on POSIX, fails the
assertions rather than passing by coincidence):

1. **Kill switch**: `install --opencode` (writer, KEEL_HOME) → `disable`
   (writer, the bonus-fixed disable.ts) → `status` (reader) asserts
   `DISABLED` appears and `enabled (enforcement active)` does not; asserts
   the sentinel file exists under `KEEL_HOME/.keel/DISABLED` and NOT under
   `HOME/.keel/DISABLED`; then `enable` (writer) → `status` (reader) again
   confirms it flips back to enabled, still fully under `KEEL_HOME`.
2. **Overrides / `KEEL_OVERRIDES_DIR` unification**: `install --opencode` →
   `allow no-verify-bypass --once` (writer, with `KEEL_OVERRIDES_DIR`
   deliberately left UNSET so the test actually exercises the `KEEL_HOME`
   fallback, not a coincidental match) → `status` (reader) asserts the
   armed override is visible; asserts `overrides.json` exists under
   `KEEL_HOME` and not under `HOME`.
